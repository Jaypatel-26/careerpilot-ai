# Phase 5 — AI job matching

## What is included

Phase 5 adds authenticated, account-backed **Find real jobs** (`/account/jobs`), job detail and match screens, **Saved jobs & matches** (`/account/jobs/saved`), and match history. The original `/jobs/match` remains a separate demo; Phase 1–4 pages and features are not replaced. Job search, details, saving and matching require a valid JWT. Saved jobs and matches are selected/deleted by authenticated owner ID. Matching sends only the selected resume report's strengths and quoted-before bullets, optional user-verified resume text and the job details to backend Gemini. Suggested missing skills from the prior report are not treated as the user's skills. The score is an estimate, not a hiring/ATS guarantee; AI may be wrong or influenced by untrusted documents. Verify all suggestions.

**Important Phase 4 privacy detail:** Original resume text was never stored as an account record. A Phase 5 match can use the previously saved AI report, but that is incomplete, fallible evidence; users can optionally upload/paste and verify the resume text for a more informed match. Extraction reuses Phase 4's PDF/DOCX upload endpoint. Inputs are sent to Gemini. Original text is not saved as a separate database field; saved match feedback and snapshots may contain personal details. Deleting a resume analysis sets a match's resume reference to null but does not delete match reports—delete those separately from Saved jobs & matches. Review Google/provider retention and privacy policies. Uploads may be temporarily buffered to disk by the web framework.

## Job source setup

The job provider reads the official Greenhouse Job Board API (`https://developers.greenhouse.io/job-board.html`). It requests public employer board metadata, descriptions and structured pay ranges; read-only endpoints need **no API key**. It never calls a user-supplied URL and it does not submit job applications. The UI displays the provider link and source; users apply on the external website. Listings and eligibility can change—check the original page. Validate the provider's and employers' terms and applicable usage/redistribution permissions for your project before public/commercial use.

For an immediately usable but **limited** feed, the default configuration queries two public boards: `gitlab,figma`. These are real provider board tokens, not a sample dataset; employer names and postings come from the provider, and current availability may change. This is not an exhaustive search of all companies, locations or Indian jobs. To change the set in Render backend Environment (no key needed):

1. Find verified public Greenhouse employer board tokens in the employer's Greenhouse board URL or official career page. Do not assume an employer uses Greenhouse.
2. Set `GREENHOUSE_BOARD_TOKENS` to comma-separated tokens, e.g. `gitlab,figma`. Maximum five unique tokens, each letters/numbers/underscore/hyphen. The application reads only those board tokens from the fixed Greenhouse domain. Verify each board and the relevant terms. Invalid configuration produces an error instead of fake jobs. An empty value disables the feed and displays a configuration notice.
3. Optional: `JOBS_CACHE_SECONDS=1800` (default 30 minutes, clamped to 5 minutes–24 hours). Cache and failed-request backoff are per application process, not shared across instances; provider outages can cause incomplete/unavailable results. Restart/redeploy after changing environment settings. More instances and cache misses mean more upstream calls. Each board response is limited to 12 MiB and 3,000 posts; overly large boards fail safely rather than silently truncating the feed. Provider API shape/terms, configured employers and job availability can change.

Search filters run against the cached configured feeds, not a global search engine. Title/company/location are substring filters; skill terms match text in the title or description and do not prove a skill is required. Workplace mode is inferred only from explicit words in title/location; experience level from explicit title keywords. Unknown and differently worded listings are excluded by those filters, so relevant jobs can be missed. The skills shown on cards are a small vocabulary of words mentioned, not a complete list of requirements. Review job descriptions and the original source. Descriptions are limited to 30,000 characters; Gemini sees at most 16,000 characters. Published date comes from provider `first_published`, updated date from `updated_at`—updated is not posted. Structured pay ranges come from Greenhouse `pay_input_ranges` when present, preserving the source label and currency; if salary is only in the text, see the description. Never infer missing salary, experience or requirements. External links are accepted only as HTTPS without credentials and opened with `noopener noreferrer`; destination content is outside CareerPilot's control.

## Deployment — GitHub, Render and Neon

1. **Back up Neon production first**, for example create a fresh branch with data and schema and make sure it is not set to delete before testing. A branch is a snapshot, not a verified restore procedure; preserve it and confirm your recovery procedure. Do not delete/change production or paste secrets into GitHub.
2. Download and unzip the complete updated source ZIP. Upload the **contents** of its `careerpilot-neon-render` folder to the existing repository's `careerpilot-neon-render` directory, preserving paths and replacing corresponding files. Do not create a nested copy. GitHub browser uploads may need each subfolder uploaded separately; confirm the new API, models, migration and frontend files are actually present. Commit the changes. Keep your old local project until verification.
3. Deploy the existing Render backend first. Preserve `DATABASE_URL`, optional `MIGRATION_DATABASE_URL`, JWT secret, Gemini key/model and frontend CORS origins. Existing build command installs `requirements.txt`; no new production dependency is required for Phase 5. Existing backend start command should remain `alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port $PORT`, run from the existing backend root. Startup applies new additive migration `d6a3b8f710e2` after `c4d7e3f912a0`. It creates `saved_jobs` and `job_match_reports` and leaves existing tables intact. The downgrade drops these two tables and destroys their data; do not run it casually. Check Render logs and `/api/v1/health/database`. If a separate `MIGRATION_DATABASE_URL` is set it must target the same database and appropriate schema as the application URL.
4. Optionally set/change `GREENHOUSE_BOARD_TOKENS` and `JOBS_CACHE_SECONDS` as described above. Never put Gemini/database/JWT secrets in frontend variables or GitHub.
5. Deploy the existing frontend from the same commit, retaining the existing root, build command `npm ci && npm run build`, publish directory `dist`, API URL environment and SPA rewrite `/*` → `/index.html`. No UI redesign or Supabase setup is needed.
6. Sign in, open **Find real jobs**, search/filter, open a listing and check the external apply link. Create or select a saved Phase 4 resume analysis; optionally upload/paste the original resume, review it, and generate a match. Verify save/remove, history after refresh, and isolation with a second account. Re-test Phase 4 resume upload and earlier text/voice interviews. If the provider or Gemini fails, check sanitized Render logs and quotas without sharing keys, database URLs, passwords or document contents.

### RLS and role ownership

The new tables enable PostgreSQL RLS with no public policies, matching the existing server-owned model. Owner isolation is enforced in application queries using JWT user IDs. PostgreSQL table owner roles ordinarily bypass RLS; the application's role must be the table owner or otherwise have correctly granted RLS bypass and table access. If a separate migration role owns the tables, the application role may be denied. Never add broad public access or disable RLS as a quick fix. Confirm Neon roles, permissions and restore procedure with your database administrator. A disposable PostgreSQL test used one owner role and checked that a granted non-owner saw no rows; production role configuration was not inspected.

## Test results and known limitations

- Frontend `npm ci && npm run build`: passed; existing large-bundle warning remains.
- Backend: 34 pytest tests passed, including owner isolation, search/filters, safe URLs, match handling, quotas, retry idempotency and Phase 1–4 tests; existing Starlette/httpx warning remains.
- Public Greenhouse provider was contacted for the default boards in a local test: search and job detail returned real provider records (390 at test time; count changes). No jobs were applied to. The automated link test checks safe URL and browser link attributes; third-party destinations can change or block access.
- Cross-origin Chromium browser tests passed for job search/filter/detail, save, match and delete with fictional provider data and mocked Gemini, plus resume, text interview and voice flows with mocked AI/speech. A mobile-width search layout check passed. No actual microphone was tested.
- Disposable PostgreSQL 17 Phase 4 → Phase 5 migration preserved existing resume and voice/interview records, tested new tables, owner access, concurrent idempotent matching and non-owner RLS. SQLite upgrade/downgrade is covered by pytest.
- **Real Gemini Phase 5 matching, live Render deployment and production Neon migration were not tested.** Real Gemini schema, quota and provider availability require post-deployment verification. Scores are estimates and do not guarantee selection.
- Per-process API/AI throttles and job caches do not coordinate across multiple workers/instances; use shared caching, rate limits and edge body/rate limits for higher traffic. Initial feed loads can be slow and a provider may become unavailable. Listings can be stale or closed. Match retries use an idempotency key while a page remains open; refreshing after an ambiguous error can cause another paid call/report, and provider/database failure after generation can incur cost without saving.
- The saved-jobs and match-history screens show up to 100 recent records; search paginates. Default boards offer limited employer/geographic coverage. AI may invent, omit or misinterpret information despite instructions; do not claim unverified skills or experience.

To run backend tests locally: `cd backend && pip install -r requirements-test.txt && pytest -q`. Frontend: `npm ci && npm run build`. Browser tests require Playwright Chromium, a disposable migrated SQLite database, the test-only mock server and a local frontend. Never run `tests.support.mockserver` in production or point tests at a real database.
